# 0002—Fenced Per-Workflow Ownership (MultiEngine)

**Status**: Accepted

## Context

Weft's checkpoint model already fences two things against a second writer. `commitCheckpoint()` routes every checkpoint, event-log, timeline, and index write through `commitFencedEngineWrite()` (`src/core/engine/fenced-write.ts`), which uses `storage.conditionalBatch()` with the checkpoint key's expected-value condition whenever the adapter reports `conditionalBatch` support. And under `ownership: 'lease'` (see [Running Weft as a Singleton Service](../../guides/singleton-service-deployment.md#optional-lease-based-ownership-for-a-clean-deploy-handoff)), that same fenced-write path additionally conditions every engine-owned write on a single, store-wide lease epoch, so a deposed instance loses its compare-and-swap and tears itself down instead of corrupting a successor's state. Both mechanisms are shipped today.

Neither mechanism stops two engine processes from both **executing** the same workflow's next step. `ownership: 'lease'` is a global single-writer lease—exactly one engine holds it for the whole store—so it already prevents two active owners by construction, but it does so by serializing the entire store behind one writer, not by letting distinct workflows progress independently on distinct engines. `ownership: 'none'`, the default, has no claim of any kind: two engines pointed at the same store can both resume the same workflow and both run its next step before either attempts the (still-fenced) write, producing duplicate side effects such as firing the same activity twice. This is the gap [Tier-0 Behavioral Contract § Concurrent Resume And Checkpoint Ownership](../../architecture/tier-0-behavioral-contract.md#concurrent-resume-and-checkpoint-ownership) names as the actual `MultiEngine` requirement: a persisted, per-workflow ownership claim acquired **before** the generator resumes, not just before the resulting write commits.

An earlier `requireConcurrentResumeSafety` flag existed to address this and was removed. It only asserted `conditionalBatch` availability at the recovery boundary—a capability check, not a claim—and never stopped two engines from both driving the same workflow's generator. `AGENTS.md` and `CLAUDE.md` both record a standing ban on reviving it under any name. This ADR does not revive it; the shape it proposes instead is a durable claim with real acquire/renew/release/takeover semantics, not a boolean assertion.

## The problem with fencing writes but not execution

A fenced write is a necessary but not sufficient correctness primitive. If two engines both resume workflow `W`, both engines run `W`'s generator to its next `yield*`, and only then do they race to commit a checkpoint—at which point the fenced write correctly picks one winner. But the loser already ran user code. If that code called an external API inside `ctx.run()`, the side effect already happened. The write-level fence closes the _storage_ race; it does nothing about the _execution_ race that precedes it. Closing that gap requires a claim that is acquired before the generator advances, not one that is only checked when a write lands.

## Decision

We add a new `ownership` mode, `workflow-lease`, that fences execution per workflow instead of fencing the whole store behind one writer. Multiple engine processes may share one durable store once each workflow has exactly one fenced owner, claimed before that workflow's generator resumes—not merely before its next write commits.

### The `ownership` option

`ownership` (`src/core/engine/ownership-options.ts`) is extended from a two-member to a three-member discriminated union: `'none' | 'lease' | 'workflow-lease'`. The default is unchanged: `'none'`. `assertKnownOwnershipMode` accepts `'workflow-lease'`; `resolveOwnershipFields` resolves two new tuning fields—`workflowClaimTtl` and `workflowClaimRenewInterval`—only when `'workflow-lease'` is selected, following the same "validate only when enabled" discipline the existing `leaseTtl`/`leaseRenewInterval` pair already uses.

Construction enforces two binary, mechanically checkable relationships through a `workflow-lease` analogue of the existing `assertLeaseTimingCoherent` check:

- `workflowClaimRenewInterval` must be strictly less than `workflowClaimTtl`—the same relationship `assertLeaseTimingCoherent` already enforces for the global lease.
- `workflowClaimTtl` must be at least `WORKFLOW_CLAIM_TTL_SAFETY_MULTIPLIER` (a fixed exported constant, default `3`) times `workflowClaimRenewInterval`.

Both relationships replace the prior, unenforceable guidance that a lease TTL should be "comfortably longer than turn duration." That guidance is moot under this design: renewal during an active turn is heartbeat-driven—a real timer, not blocked by a synchronous `await` on an in-flight activity—so the TTL only ever needs to survive one missed heartbeat cycle, never the turn's own duration.

`workflow-lease` is mutually exclusive with `lease` by construction—they are different members of one discriminant field—and that exclusivity is now enforced across engine _processes_, not only within one process, by a store-wide **ownership-mode marker** (see [Construction-time capability gates](#construction-time-capability-gates) below). `ownership: 'none'` engines never touch the marker; mixing `'none'` with a fencing mode remains an undetected operator responsibility, exactly as it was before this ADR—not a new regression, and deliberately out of scope (see [Open questions](#open-questions)). `workflow-lease` is also rejected when combined with `detectSecondInstance: true`, for the same reason `'lease'` already is: second-instance detection assumes a single global owner. Unlike `'lease'`, `workflow-lease` is **not** rejected when combined with `backgroundTasks: 'manual'`—`runMaintenance()` is extended to drive per-workflow claim renewal, for every claim the engine holds, on every awaited host tick, the same way it already drives `scheduler.tick`/cleanup/retention/alerts.

### The durable claim keyspace

Ownership under `workflow-lease` is tracked with two per-workflow keys and one store-wide singleton marker, all registered through the existing `storageConditionalBatch`/`KEYS.*`/`WEFT_RESERVED_KEY_PREFIXES` process:

- `wf-owner-epoch:<workflowId>`—the fencing token. Changes only on `acquire` or `takeover`. **Permanently retained**: never deleted by release, purge, retention, or downgrade, so it stays valid as an ABA-safe token across the entire lifetime of a workflow id, including reuse via `onTerminalConflict: 'start-new'`.
- `wf-owner-holder:<workflowId>`—the holder record. Changes on `acquire`, `takeover`, and `renew`. Deleted **only** at terminal-state commit or an explicit `engine.suspend()` commit—critically, _not_ at ordinary park (sleep, wait-signal, wait-update, wait-condition, wait-async-activity, await-child-completion).
- `ownership-mode-marker`—a store-wide singleton, `{ mode: 'lease' | 'workflow-lease', establishedAt: number }`, written once by the first fencing-mode engine to construct against a fresh store and compared by every subsequent fencing-mode engine at construction.

The epoch key uses the same 8-byte big-endian `uint64` codec `src/core/engine/lease-codec.ts` already uses for the global lease epoch, parameterized by workflow-scoped key instead of reimplemented. The holder key and the marker key use the same strict-JSON, fail-closed-to-`null` codec discipline. Every `acquire`—including the very first one for a never-before-seen workflow id—reads `wf-owner-epoch:<workflowId>` first and mints the new epoch as `(lastReadEpoch ?? 0) + 1`. There is no code path, including a brand-new id's create-batch or an `onTerminalConflict: 'start-new'` restart of a previously purged id, that writes a hardcoded literal epoch. This closes the ABA hazard: a stale zombie engine's cached epoch from a prior "generation" of a reused workflow id can never accidentally match a fresh generation's epoch, because the counter is never reset.

The holder record's four fields are compared as one opaque, byte-equal blob wherever a `conditionalBatch` precondition names `wf-owner-holder:<workflowId>`; there is no per-field precondition at the storage layer. The table below marks every field as compared for that reason, while distinguishing which fields actually carry safety weight from which merely ride along inside the same encoded value.

| Field       | Type                                                     | Compared (byte-equal in the precondition) | Purpose                                                                                                                                                                                                                                                                            |
| ----------- | -------------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `engineId`  | `string`                                                 | Yes                                       | Holder identity, `crypto.randomUUID()` minted once per engine process—the same shape as the global lease's `holderId`. Identifies who to blame on a lost race and is the value `wakeOwnershipCheck` compares against a locally cached context to decide whether it is still valid. |
| `epoch`     | `uint64` (also embedded as a JSON number in this record) | Yes                                       | The workflow-scoped fencing token appended as a precondition on every `commitFencedEngineWrite` scoped to this workflow id while `workflow-lease` is active. Monotonic for the lifetime of the id; never reset. This is the field that actually carries write-safety weight.       |
| `expiresAt` | `number` (safe non-negative integer, engine-clock)       | Yes                                       | Read and interpreted by application code only, as the liveness signal feeding the `expire` judgment. It is not itself a safety mechanism—the CAS is—and its practical effect is bounded by a fixed grace multiplier (see `expire`/`takeover`) rather than compared raw.            |
| `claimedAt` | `number` (safe non-negative integer, engine-clock)       | Yes                                       | When the _current_ epoch was first claimed; unchanged across renewals of that epoch and unchanged across the cadence switch between active-turn heartbeat renewal and parked scheduler-tick renewal. Diagnostics and operator visibility only.                                     |

The stated guarantee is scoped precisely: exactly one owner's **durable writes** survive for a given epoch. It does not claim exactly one owner's **user-code execution** is exclusive at every instant—see [Mixed-version rollout, downgrade, and rollback](#mixed-version-rollout-downgrade-and-rollback) for the bounded, documented window this implies.

### Ownership transitions

| Transition | Precondition                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Effect                                                                                                                                                                                                                                                                                                                                                                   | On precondition failure                                                                                                                                                                                                                                                                                                                                                                         |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `acquire`  | `conditionalBatch`: `wf-owner-holder:<id>` expected `null` (absent) AND `wf-owner-epoch:<id>` expected the exact bytes just read for that key (`null` if genuinely never written; the true prior epoch if the id was previously claimed and later released or purged). `acquire` always performs this read first—it never assumes absence.                                                                                                                                                               | Atomically: epoch key becomes `(lastReadEpoch ?? 0) + 1`; holder key becomes `{ engineId, epoch: newEpoch, expiresAt: now() + claimTtl, claimedAt: now() }`. Folded into the same atomic batch as the enabling write—the create-batch for a start, or the pending-to-running transition for a delayed-start fire.                                                        | `lost-race`: another engine's holder is present and, by this engine's clock, not past the grace window (see `expire`). Background scanners (`recoverAll`, scheduler tick) skip this workflow this cycle; an explicit single-workflow caller (`engine.resume(id)`) throws `WorkflowClaimUnavailableError`.                                                                                       |
| `renew`    | `conditionalBatch`: `wf-owner-holder:<id>` expected the exact holder bytes this engine last wrote. The epoch key is not conditioned on separately—any epoch change already changes the holder bytes. Two cadences share this transition: an active-turn heartbeat timer (unaffected by a synchronous `await` on an in-flight activity) and a parked-claim cadence driven by this engine's own `Scheduler#tick` (or `runMaintenance()` under `backgroundTasks: 'manual'`).                                | Holder key rewritten with the same engine id and epoch, a fresh `expiresAt`, and the _same_ `claimedAt`. Standalone commit.                                                                                                                                                                                                                                              | Immediate self-deposition for this one workflow: abort in-flight work via that workflow's `AbortSignal` (active-turn case) or synchronously clear all local in-memory park state (parked case), refuse further checkpoint commits for the in-progress turn, and emit `WeftWorkflowClaimLostWarning`. This is best-effort/fast detection; the next attempted write's CAS is the actual backstop. |
| `release`  | `conditionalBatch` conditions folded into the same atomic commit as reaching a terminal or suspended state (complete, fail, cancel, timeout, or an explicit `suspend` commit): `wf-owner-epoch:<id>` expected this engine's cached epoch bytes AND `wf-owner-holder:<id>` expected this engine's last-known holder bytes. `release` fires **only** here—never at ordinary park.                                                                                                                          | Deletes `wf-owner-holder:<id>` only; `wf-owner-epoch:<id>` is never deleted. Because release no longer fires at ordinary park, a workflow parked on sleep or wait-signal keeps its holder record continuously renewed by the same engine that parked it.                                                                                                                 | The enclosing terminal/suspend commit fails atomically. This is correct, not a special case—a holder-bytes mismatch here means this engine was already fenced out before it could park or terminate cleanly. Recovery proceeds from the last checkpoint that did commit.                                                                                                                        |
| `expire`   | An observed condition, not a storage transition: `holder.expiresAt` (from the last bytes read) plus a fixed grace multiplier, `WORKFLOW_CLAIM_TAKEOVER_GRACE_MULTIPLIER` (default `2`, applied to `workflowClaimRenewInterval`), is earlier than this engine's own clock. The grace term dampens clock-skew-driven false-expiry judgments.                                                                                                                                                               | No write. Enables a subsequent `takeover` attempt. The judgment carries no weight for write safety—the CAS is what is safe—but it does carry weight for execution exclusivity: a wrong staleness judgment opens a real, bounded window in which the deposed engine's already-dispatched, non-abort-checking activities can complete before its next write loses its CAS. | Not applicable—nothing to fail; only the subsequent CAS carries write-safety weight.                                                                                                                                                                                                                                                                                                            |
| `takeover` | `conditionalBatch`: `wf-owner-holder:<id>` expected the exact stale holder bytes last read AND `wf-owner-epoch:<id>` expected the exact epoch bytes read alongside it. Only attempted after `expire`'s grace-adjusted judgment. A per-workflow-id anti-thrash cooldown applies after this engine loses ownership via a failed `renew`: an exponential backoff starting at `workflowClaimRenewInterval`, capped at `workflowClaimTtl` × 4, cleared on the next successful acquire or takeover of that id. | Atomically: epoch key becomes `readEpoch + 1` (from the value just read, never self-reported); holder key becomes a fresh `{ engineId, epoch: newEpoch, expiresAt: now() + claimTtl, claimedAt: now() }`.                                                                                                                                                                | `lost-race`: the record already changed since the read. Abandon, re-read, and back off, bounded at 5 attempts within this takeover cycle. The metric outcome is `lost_race`, or `backoff_skipped` if the anti-thrash cooldown suppressed the attempt entirely.                                                                                                                                  |

Two additional transitions round out the mechanism without changing the five above. `acquire (standalone resume)` is a named exception to `acquire`'s "never a standalone commit" rule, required for the single most common recovery case: a workflow left `status: 'running'` at crash time, where there is no other enabling write to fold a claim into. It uses the identical conditions and effect as `acquire`/`takeover`, attempted in `resumeWorkflowFromStorage`/`performSerializedResume` **before** the `onRecoveredWorkflow` hook and before the generator relaunches; it is safe as a standalone commit because every subsequent write for the resumed turn already carries the resulting epoch as its own condition. `wakeOwnershipCheck` is a read-only re-read of `wf-owner-holder:<id>` performed immediately before any code path resolves an in-memory waiter or drives a generator for a parked workflow. A match proceeds as a cheap pre-check—the subsequent durable write still carries the epoch as the real backstop. A mismatch means this engine was deposed while parked: the in-memory resolver is discarded, the generator is not driven, and `WeftWorkflowWakeDiscardedWarning` is emitted for operator visibility.

### Distinct workflows on distinct engines

Both per-workflow keys are parameterized by `workflowId`, so the claim mechanism has no shared key to contend on: an engine holding `wf-owner-holder:X` and an engine holding `wf-owner-holder:Y` are independent `conditionalBatch` compare-and-swaps against independent keys. Distinct workflows _can_ progress concurrently on distinct engines under `workflow-lease`—that is the entire point of the mode. Recovery preflight scanning changes from an in-process ownership-flag check to a real per-workflow `acquire` attempt (or the `acquire (standalone resume)` transition for the common running-status case); a workflow another engine validly holds fails that engine's CAS and is skipped, so recovery scanning becomes a natural work-partitioning mechanism across engines sharing a store.

That partitioning is deliberately coarser than the pre-ADR design once a workflow is claimed. Because ordinary park no longer releases the claim—it is renewed on a scheduler-tick cadence instead—a parked workflow is _not_, in the steady state, up for grabs by another engine; it only becomes acquirable via `takeover` after a genuine crash (missed renewals past the grace-adjusted `expire` judgment). This closes the sleep-wake and signal-wake split-brain hazards a release-on-park design would create, at the cost of every parked workflow belonging to a single fixed engine until it crashes or explicitly suspends or terminates. Self-balancing work distribution still applies at the point workflows are first claimed—start, delayed-start fire, and recovery of a crashed workflow—just not through cheap re-acquisition during ordinary park.

### Mixed-version rollout, downgrade, and rollback

Rollout is safe only when every one of the following holds:

- Every engine process pointed at the shared store implements per-workflow claim CAS for every entry point in the classification table above—no engine silently bypasses claim-checking.
- The storage backend reports `conditionalBatch: true`, enforced synchronously at construction (Gate 1, below).
- Every engine sharing the store passes the ownership-mode-marker check (Gate 2, below)—mechanically enforced at construction, not merely documented.
- `workflowClaimRenewInterval < workflowClaimTtl` and `workflowClaimTtl >= WORKFLOW_CLAIM_TTL_SAFETY_MULTIPLIER × workflowClaimRenewInterval`, both validated at construction.
- Under `backgroundTasks: 'manual'`, the host calls `runMaintenance()` strictly more often than `workflowClaimRenewInterval` for every claim this engine currently holds.

Rollout is unsafe under any of the following:

- A partial rollout where some engines predate this feature and carry no claim-checking code, including no ownership-mode-marker check. The marker protects new-code engines from each other; it cannot protect against an old binary that never checks it at all.
- A `conditionalBatch: false` storage backend, which Gate 1 rejects at construction.
- Clock skew between engine processes exceeding `workflowClaimTtl - WORKFLOW_CLAIM_TTL_SAFETY_MULTIPLIER × workflowClaimRenewInterval`, which causes false-expiry `expire` judgments. This is a precise, numeric threshold, but the operator's actual skew is an environmental property this ADR cannot mechanically verify—bound it with NTP or chrony.
- Treating a wrong staleness judgment as a liveness-only concern. It is a bounded **correctness** caveat: the deposed engine's already-in-flight, non-abort-checking synchronous activities can complete and produce real side effects before its next write loses its CAS. Activities must be idempotent or side-effect-safe regardless of ownership configuration—this was already true, and remains true.
- Under `backgroundTasks: 'manual'`, a host that does not call `runMaintenance()` faster than `workflowClaimRenewInterval`, which produces spurious self-deposition churn for its own legitimately live claims.

Downgrading a store from `workflow-lease` back to `none`/`lease` is correctness-safe: neither mode reads or conditions on `wf-owner-*` keys. `wf-owner-holder` keys are garbage-collected by the extended purge/retention delete batch; `wf-owner-epoch` keys are deliberately never deleted and remain as harmless orphans, bounded in count by the total distinct workflow ids the store has ever seen. The `ownership-mode-marker` key is also left in place on downgrade—it records what the store _was_ configured as—and an operator reusing the store under a different fencing mode with zero engines active may delete it as an explicit administrative action.

Rolling back the _engine binary_ itself to a pre-`workflow-lease` version while more than one engine remains pointed at the shared store is unsafe: the old binary has no claim-checking code and no ownership-mode-marker check, so it executes workflows unconditionally and is not even blocked by Gate 2, which only new-code engines enforce against each other. Scale down to a single engine process, or stop all engines, before rolling back binaries.

### Construction-time capability gates

`Engine.create()` performs two sequential gates, both before `recoverAll()`, scheduler construction and start, and task-queue/long-poll wiring, extending the existing `ownership: 'lease'` check.

**Gate 1—storage capability.** Fires for `ownership: 'lease'` or `ownership: 'workflow-lease'`. Reuses the existing, untyped `Error` that `requireStorageCapability` already throws (`src/storage/capabilities.ts`). There is no stable error code on this path—a pre-existing gap across all `requireStorageCapability` call sites, not patched by this ADR, and tracked as a candidate follow-up to promote it to a typed `WeftError`. The diagnostic message is definitive, not conditional on a future verification step: "Storage adapter does not support the required `conditionalBatch` capability, which is needed for workflow-lease ownership."

**Gate 2—ownership-mode marker.** New. Fires immediately after Gate 1 passes, for the same trigger. Reads the store-wide `ownership-mode-marker` key. If absent, this engine `conditionalBatch`-puts `{ mode: thisEngine'sConfiguredMode, establishedAt: now() }` with an expected value of `null`; on a CAS loss it re-reads and compares. If the stored mode—from either the initial read or the post-CAS-loss re-read—differs from this engine's configured mode, construction fails closed with the new, typed `OwnershipModeMismatchError` before any recovery proceeds. `OwnershipModeMismatchError` carries a stable `WeftErrorCode` and three fields: `configuredMode` (this engine's `ownership` option), `storedMode` (the mode read from the marker), and `establishedAt` (the marker's timestamp, for diagnosing when the mismatch was introduced). `ownership: 'none'` engines never touch the marker.

## `ownership: 'lease'` is not replaced

`ownership: 'lease'` is unchanged by this ADR: it remains the global single-writer mode, with one `lease:epoch`/`lease:holder` pair for the whole store and the same rolling-deploy handoff behavior it has today. `workflow-lease` is a mutually exclusive _alternative_, not a successor—choose `lease` when a single global owner with a clean handoff is what you want, and `workflow-lease` when distinct workflows genuinely need to progress on distinct engines. The exclusivity between the two is now enforced at runtime, across processes, by the ownership-mode marker (Gate 2) rather than by prose alone. `ownership: 'none'` is likewise unchanged—zero fencing, single-engine-only—and the standing ban on reviving `requireConcurrentResumeSafety` under any name is unaffected by this ADR and remains permanent.

## Why not

**A separate capability boolean (`enableMultiEngine: true`) layered alongside `ownership`.** This is the "please be safe" shape the accepted contract explicitly rules out. A boolean flag has no discriminant relationship with `'lease'`, so nothing would stop an operator from setting both, and mixed-mode ambiguity—the exact hazard the ownership-mode marker exists to close—would persist undetected. Folding the new mode into the existing `ownership` discriminated union makes the two mutually exclusive by construction instead of by documentation.

**Reviving `requireConcurrentResumeSafety` under any name.** This is permanently banned per `AGENTS.md` and `CLAUDE.md`, and this ADR does not touch that ban. It is also the wrong shape on the merits, independent of the ban: the original flag only asserted `conditionalBatch` availability at the recovery boundary—a one-time capability check—and never established a durable per-workflow claim. A capability assertion tells you the _storage_ can support fencing; it says nothing about whether any given workflow currently has exactly one owner. Two engines could both pass that assertion and still both resume the same workflow.

**A capability-only assertion with no behavior change (`requireConditionalBatchForMultiEngine: true`).** Same defect as above in a different name. `conditionalBatch` support is a precondition of selecting `workflow-lease`—Gate 1 already enforces it—but the precondition is not the mechanism. Shipping only the precondition check, with no claim keyspace and no acquire/renew/release/takeover transitions behind it, would document a requirement without building the thing that requirement gates.

**Making the ownership-mode marker optional or opt-out.** An optional marker would recreate exactly the undetectable-mixed-mode hazard—a `'lease'`-mode engine silently coexisting with `'workflow-lease'`-mode engines against the same store—that the marker exists to close. It is mandatory and unconditional for both `'lease'` and `'workflow-lease'`; making it skippable would turn a closed hazard back into an open one for the sake of configurability nobody asked for.

## Consequences

- Two engine processes may now share one durable store, provided every engine implements the full claim protocol above and the storage backend supports `conditionalBatch`. Single-engine-per-store remains the supported topology whenever any engine in the fleet predates this feature.
- `claimActivityReconciliationStart` must gain a `wf-owner-epoch:<id>` precondition before `workflow-lease` ships; this is now a named implementation prerequisite rather than an open question.
- `query()` and `tryInlineUpdateHandler` must stop silently returning `undefined` on a non-owning engine; the routing mechanism for a non-owning hit is still open (see below), but the silent-failure bug itself must be fixed regardless of which mode is configured.
- Activities remain required to be idempotent or side-effect-safe independent of `ownership` configuration—this ADR documents an existing, unavoidable correctness caveat around a wrong `expire` judgment rather than introducing a new one.
- Two documentation statements that predate the checkpoint-CAS and lease-epoch work—[Tier-0 Behavioral Contract](../../architecture/tier-0-behavioral-contract.md#concurrent-resume-and-checkpoint-ownership) and [Running Weft as a Singleton Service](../../guides/singleton-service-deployment.md)—are corrected alongside this ADR to describe the checkpoint-write CAS and the global lease as shipped, while continuing to state plainly that the per-workflow execution claim this ADR specifies does not exist in the runtime yet.

## Open questions

- Exact default values for `workflowClaimTtl`, `workflowClaimRenewInterval`, `WORKFLOW_CLAIM_TTL_SAFETY_MULTIPLIER` (proposed `3`), and `WORKFLOW_CLAIM_TAKEOVER_GRACE_MULTIPLIER` (proposed `2`). The mechanism and relationships are fully specified and binary-checkable; the numeric constants are not yet fixed.
- The exact backoff curve and cap for the per-workflow-id takeover cooldown (proposed: exponential starting at `workflowClaimRenewInterval`, capped at `workflowClaimTtl` × 4).
- Whether recovery preflight scanning should attempt claims for all recoverable candidates immediately at boot, or use jittered ordering to avoid a thundering herd. A liveness/efficiency question, not a correctness one.
- Whether `query()`/`update()` routing to the true owning engine should be real cross-engine forwarding (a new inter-engine RPC surface that does not exist today) or a "not locally owned, retry against the owner" error surfaced to REST/JSON-RPC callers. Fixing the silent-`undefined` bug is a hard requirement either way; only the routing mechanism is open.
- Whether `assertDurableStorageForRecovery` should be wired into `Engine.create()` specifically for `ownership: 'workflow-lease'`, given `MultiEngine` deployments are the most exposed to weak-read-consistency backends causing wasted claim-CAS contention.
- `documentation/roadmap-to-1.0.md` needs a dedicated follow-up read against this ADR's actual scope before any correction is drafted there; it is intentionally not corrected as part of this ADR.
- Whether the ownership-mode marker should also apply to `ownership: 'none'` engines mixed with fencing-aware engines against the same store. Deliberately scoped out here, since extending it to `'none'` would be a behavior change for every existing default-configured deployment.
- Cross-engine parent/child completion has no durable notification path. A parent awaiting `ctx.startChild()` under the default `parentClosePolicy` blocks on `childHandle.result()`, which resolves through `internals.resultResolvers`—an in-memory `Map<string, WorkflowResultWaiter>` (`src/core/engine/internals.ts`) settled only by the terminal paths in `src/core/engine/termination/complete.ts`. If the parent is owned by engine A and the child is claimed by engine B, engine B's terminal transition settles engine B's map and engine A's parent waiter never fires. Making the parent claim-requiring is therefore necessary but not sufficient: `workflow-lease` additionally needs either a durable child-terminal notification the parent's owner can observe, or a rule that a child is always claimed by its parent's owner. Choosing between those is open, but shipping the mode without one of them would strand awaited children across engines.
