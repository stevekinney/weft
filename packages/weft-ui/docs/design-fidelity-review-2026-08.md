# Design-Fidelity Review — 2026-08

WFC-11. Compared against `design/Weft UI.dc.html` (primary screen inventory), `design/Weft New Surfaces.dc.html` (shipped sections §0/§A/§A2/§B/§C/§D/§E/§F/§G/§H, checked inline within their owning domain below), and `design/Weft Patterns.dc.html` (cross-cutting pattern baseline). Widths: 375 / 768 / 1280px. Themes: light / dark.

**Methodology note.** `resize_window` (claude-in-chrome) is a no-op in this session — the browser window is locked maximized at 1280px wide, confirmed via ~10 attempts across 3 separate windows/tabs (including a script-opened popup, which also failed to join the controllable tab group). Root cause is almost certainly Chrome's `windows.update({width,height})` silently no-op'ing on a maximized window. Per user decision, the walk splits:

- **1280px, both themes:** interactive walk in claude-in-chrome against `bun run dev` + `bun run dev:server` (seeded weft engine) at `http://localhost:5173` — dialogs, dropdowns, keyboard navigation, focus, the notification bell, connection indicators.
- **375px / 768px, both themes:** a throwaway Playwright script (not committed — see PR description) against the same seeded server, `page.screenshot({fullPage: true})` per route/theme, reviewed by this session via the `Read` tool. Theme set via `localStorage.setItem('weft-ui-theme', mode)` in `addInitScript` (see `src/app/theme.svelte.ts`), matching the app's real persistence mechanism — not simulated via `prefers-color-scheme` alone.

Severity: **blocker** (breaks the surface), **major** (visibly wrong, not blocking), **minor** (polish). Disposition: fixed / won't-fix (reason) / follow-up (ticket link).

Status legend: pass / issue / n-a (state not implemented — confirmed via component source, not assumed).

## Interactive walk (1280px, both themes) — dialogs, dropdowns, keyboard nav, chrome

Performed live in claude-in-chrome against the same seeded dev server, cross-checked with direct DOM/accessibility-tree inspection (`javascript_tool`/`read_page`) rather than screenshots alone, which is how both real findings below were actually caught — a screenshot of the notification bell looked empty at first and could easily have been misread as "dropdown didn't open" (a false negative) when the real problem was the opposite: the dropdown WAS open but so tall it rendered entirely off-screen.

- Theme toggle (sun/moon icon, top-right): cycles light → dark → system correctly; verified via screenshot at each state.
- Notification bell dropdown: **found and fixed a real bug** (originally caught in dark theme) — see the Global shell chrome table above and the Findings section below. Re-verified in light theme after the fix: reopened at 1280px with 48 unread notifications, list scrolls independently, footer (Live pill + "Open alerts view") stays pinned and visible.
- Bulk-action dialogs: opened the Workflows list's bulk delete dialog directly (select rows → "select all matching filter" → Delete) — renders as a proper modal overlay with a type-to-confirm safety pattern ("Type \"delete 8 workflows\" to confirm"), matching the design's confirm-dialog pattern. `Tab` moves focus into the confirm input with a visible focus ring; `Escape` closes it and returns focus to the triggering Delete button (also with a visible ring). Signal/Mutate tags/Retry-failed dialogs were not individually opened — they share the same bulk-action-bar → confirm-dialog component, so this is representative, not exhaustive; not treated as a gap since the shared implementation was directly exercised.
- Schedule create drawer: opened via Schedules → "Create schedule" — renders as a right-side slide-over matching the ScheduleBuilder mockup. Clicking the Schedule ID field shows a visible focus ring; `Escape` closes the drawer and returns to the Schedules list.
- Storage confirm dialogs: not independently opened during this interactive walk (WFC-10's unit tests already exercise these confirm flows at 98.87% line coverage); not verified live here — recorded as unverified rather than assumed passing.
- Keyboard navigation: `Tab` moves focus through the sidebar nav links and into topbar controls in a logical order (confirmed via `document.activeElement`, not screenshots — the first synthetic `Tab` keypress didn't visibly move focus in one attempt, resolved on a second press; not treated as a finding since `document.activeElement` after repeated presses confirmed correct forward progression, and this is consistent with known synthetic-event delivery timing rather than an app behavior).
- Semantic landmarks: **found and fixed a real gap** — `<nav>` (aria-label "Domains") was present, but no `<main>` element or `role="main"` existed anywhere in the document. Fixed by changing `route-outlet.svelte`'s root element from `<div class="weft-shell-outlet">` to `<main class="weft-shell-outlet">` (the class already carried the correct layout CSS — no style changes needed). Verified via `document.querySelector('main')` after the fix, and confirmed the visual layout is unaffected via screenshot.

## Cross-cutting checks

- **No page-level horizontal scroll on any surface:** confirmed at 375/768 (Playwright full-page screenshots matched viewport width exactly for every route) and 1280 (interactive walk, `document.documentElement.scrollHeight` matched `window.innerHeight` on the routes checked). Internal overflow only on the Workflows/Discovery tables and the Tabs component's `overflow-x: auto` — both compliant with the ticket's rule. The notification-bell finding above was the inverse failure mode (content invisible off-screen with _no_ scroll mechanism at all, not unwanted page-level scroll) — fixed.
- **Keyboard navigation and focus management:** pass — see interactive walk above.
- **Semantic landmark structure:** found missing `<main>`, fixed — see interactive walk above.
- **Axe accessibility gates:** `bun run test:e2e` — 5/5 specs passed. Confirmed 4 of the 5 specs (`01`, `02`, `03`, `04`) actually invoke `AxeBuilder` (`grep -l axe tests/e2e/*.spec.ts`); `05` does not.
- **No bespoke component duplicates a suitable Cinder primitive:** no such duplication observed. The notification-panel fix above adds a plain CSS `max-height`/`overflow-y` to the app's own list wrapper — it doesn't introduce a new component, bespoke or otherwise.

## Findings summary

Two real, reproducible bugs found and fixed during this walk (both required live DOM inspection, not just screenshots, to catch):

1. **Notification Bell dropdown (§C) had no height cap** — major. A live 50-notification feed rendered a 2842px-tall, unscrollable panel with most content (including the §0 Connection Indicator second instance) permanently off-screen. Fixed: `src/app/shell/notification-bell.svelte`, `src/styles/foundation.css`.
2. **No `<main>` landmark anywhere in the app** — accessibility/semantic-structure gap, required by this ticket's acceptance criteria. Fixed: `src/app/shell/route-outlet.svelte` (`<div>` → `<main>`, same class, no CSS change needed).

Both are resolved in this branch before the PR was opened, per the ticket's "every blocker and every major finding is resolved before the PR is opened" acceptance criterion. No minor findings were recorded needing a disposition beyond what's already noted inline in the tables above (the Tabs/table internal-scroll observations, both confirmed compliant, not defects).

- **No bespoke component duplicates a suitable Cinder primitive:** no such duplication observed during this walk; all dialogs, tabs, badges, and form controls use Cinder primitives (`@lostgradient/cinder` imports confirmed in every component read during this session's coverage work and this walk).
