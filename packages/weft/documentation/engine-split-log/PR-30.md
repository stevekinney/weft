# PR 30 — Engine lifecycle extraction

## Scope

Extracts workflow lifecycle methods from `src/core/engine/index.ts` into
`src/core/engine/lifecycle.ts`.

This follows the PR 8 `EngineInternals` sibling-module pattern: lifecycle
functions take `EngineInternals` first, receive typed parameters, and call back
into engine-only behavior through `LifecycleCallbacks`.

## Files added/changed

- `src/core/engine/lifecycle.ts` — new lifecycle sibling module containing
  start, recovery, resume, fork, version-preparation, start-header, initial
  state, search-attribute, and replay-update helpers.
- `src/core/engine/index.ts` — lifecycle entrypoints now delegate into
  `lifecycle.ts`; schedule and timer callbacks call lifecycle helpers directly.
- `documentation/engine-split-log/PR-30.md` — this split log.

## Replay-determinism rules respected

- `startWorkflow` keeps the original await order; no `Promise.all` was added.
- `resumeWorkflowFromStorage` keeps the original load, preparation, event-log
  restoration, header restoration, serialized state write, dispatch, and
  replay-update scheduling order.
- No await boundaries were merged or reordered.
- Generator adoption and continuation order is unchanged.
- Event emission positions relative to storage writes are unchanged.
- Storage batch composition remains equivalent to the pre-extraction code.

## Implementation notes

`EMPTY_STORAGE_VALUE` and `FORK_LINEAGE_ATTRIBUTE` moved into
`lifecycle.ts`; `EMPTY_STORAGE_VALUE` is imported back into `index.ts` for the
remaining terminal-cleanup tracking helper.

`#createWorkflowHandleWithResultPromise`, `#cacheHandle`,
`#processPendingUpdatesForHandlers`, and terminal cleanup helpers remain in the
engine because they are used by non-lifecycle paths.

## Dependent PRs

PRs after 30 can continue removing remaining engine methods from
`src/core/engine/index.ts`. The `core-engine-file-length` disable remains in
place until a later PR drops the file below the threshold.
