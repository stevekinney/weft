Address WFT-19 PR review round 6 (Codex): fail closed on ambiguous
per-instance pins, persist fork's resolved revision durably

Two fresh P1 findings on the round-5 diff, both real gaps one layer
below the identity-cache fix:

1. getResolvedDynamicRegistration()'s sync-only fallback used
   lastResolvedRevisionByName unconditionally for revision === undefined
   -- correct for a type's sole registered candidate, but genuinely
   ambiguous with two or more. This let workflow-retention-deadline.ts
   purge a legacy record early under a sibling's shorter retention
   window (irreversible), let finalizer-registration.ts run a sibling's
   finalizer, and let listing.ts's setAttributes() validate against a
   sibling's schema -- all bypassing the legacy-ambiguous classification
   each caller's own async fallback would otherwise reach. The fallback
   now gates on canResolveRevisionLocally(), returning undefined with
   2+ candidates so the async path fails closed. retention.ts's
   resolveWorkflowTypeRetention() -- the one genuinely type-level caller
   with no instance to pin against -- keeps the permissive answer via a
   new resolveLastKnownDynamicRegistration() export.

2. A legacy fork's durable state never got the resolver's resolved
   revision, only its in-memory identity cache did (round 5).
   createForkedWorkflowState() stamped the fork's persisted `revision`
   with sourceState.revision -- the source's still-undefined legacy pin
   -- even though fork()'s resolver had already resolved the type's
   sole candidate. The fork ran correctly until the next restart, but a
   fresh-process recoverAll() after a second candidate registered would
   classify the durably-unpinned fork legacy-ambiguous and refuse to
   resume it. createForkedWorkflowState() now stamps
   `sourceState.revision ?? resolvedRevision` -- the resolver's answer
   fills in ONLY when the source's own persisted revision is itself
   undefined. (Stamping the resolver's revision unconditionally, tried
   first, regressed every eager-type fork's persisted revision --
   resolveExecutableRegistrationForRevision() always returns
   revision: undefined for an eager registration, distinct from the
   real value resolveCachedStartRevision() stamps at ordinary start
   time -- caught by tests/replay-fixtures/fork-from-checkpoint.json's
   golden byte comparison before landing.)

New regression tests: workflow-retention.test.ts proves a legacy
record with 2+ candidates survives a sweep past a last-resolved
sibling's short retention window; dynamic-source-recovery.test.ts
asserts a fork's persisted revision directly and proves a fresh-process
recoverAll() resumes it after a second candidate registers. Both
confirmed to fail on the pre-fix code and pass after.
